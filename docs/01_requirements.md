# 01. 要件定義

## 1. 用語

| 用語 | 意味 |
|---|---|
| リポジトリ (Repository) | GitHub上のGitリポジトリ。アプリでは `owner/name` で識別する |
| ベースコミット (base commit) | アプリがツリーとファイルを取得した時点のブランチ先頭コミットSHA。編集・diff・commitの基準 |
| 保留中の変更 (PendingChange) | ユーザーまたはAIがローカルで加えた、まだcommitされていないファイル単位の変更 |
| ワークスペース (Workspace) | 1つのリポジトリ・1つのブランチに対するローカル状態（ベースコミット + キャッシュ + 保留中の変更） |
| ビューア (Viewer) | ファイル種別ごとの表示コンポーネント（PDF、Markdown、Notebook、コード） |
| エージェント (Agent) | Claude APIをツール利用で回し、リポジトリの調査・編集を行うAI層 |
| ツール (Tool) | エージェントが呼び出せる操作（`read_file` など） |
| 承認 (Approval) | AIが提案した変更やcommitをユーザーが明示的に許可する行為 |
| 実行バックエンド (ExecutionBackend) | Python/R/Quartoを実行するリモート環境（Jupyter Server / JupyterHub） |

## 2. スコープ

### 2.1 対象プラットフォーム

| 項目 | 内容 |
|---|---|
| OS | iOS 16 以上（iPad優先、iPhone対応）、Android 9 (API 28) 以上（タブレット優先、スマートフォン対応） |
| 画面 | 幅 600dp 以上をタブレットレイアウト、未満をフォンレイアウトとする（§FR-80） |
| 入力 | タッチ、ハードウェアキーボード、スタイラス（Phase 4のPDF注釈で使用） |
| ネットワーク | オンライン前提。キャッシュ済みファイルはオフラインで閲覧可（NFR-20） |

### 2.2 フェーズとスコープ

| Phase | 名称 | 主なスコープ | 対応要件 |
|---|---|---|---|
| 1 | 閲覧中心のMVP | 認証、リポジトリ選択、ツリー、PDF/Markdown/ipynb/コード表示、キャッシュ、単一ファイルへのAI質問 | FR-10〜15, FR-20〜24, FR-26, FR-30〜35, FR-37, FR-60〜62, FR-68〜69, FR-80〜83 |
| 2 | 編集とGitHub反映 | テキスト編集、Notebook編集、保留中の変更、diff、commit/push、AIによる編集提案と承認 | FR-40〜47, FR-63〜66 |
| 3 | 実行環境接続 | Jupyter Server接続、Python/R実行、Notebook出力更新、Quarto render | FR-70〜74, FR-67 |
| 4 | 研究ライブラリ化 | PDF注釈、全文検索、メタデータ、BibTeX | FR-90〜95 |
| 5 | 共同研究 | branch/PR、レビュー、権限 | FR-100〜103 |

Phase 1 と 2 を合わせて「MVP」と呼ぶ。本設計書はPhase 1〜3を詳細に、Phase 4〜5を概要レベルで規定する。

## 3. 機能要件

MUST = そのPhaseの完了条件。SHOULD = 可能なら実装。MAY = 任意。

### 3.1 認証・リポジトリ（FR-1x）

|---|---|---|---|

| FR-11 | 取得したアクセストークンは端末のセキュアストレージに保存し、再起動後も再ログイン不要 | MUST | 1 |
| FR-12 | ユーザーはログアウトでき、ログアウト時にトークンとキャッシュ内の非公開データを削除できる | MUST | 1 |
| FR-13 | ユーザーがアクセス権を持つリポジトリ（own / collaborator / organization）を一覧し、検索・選択できる | MUST | 1 |
| FR-14 | 直近に開いたリポジトリを起動時に復元する | SHOULD | 1 |
| FR-15 | 複数リポジトリを切り替えられる（同時に開くのは1つ） | MUST | 1 |

| ID | 要件 | 優先度 | Phase |
|---|---|---|---|

| FR-42 | Notebookの Markdown セル・コードセルのソースを編集、セルの追加・削除・移動ができる。出力は保持する | MUST | 2 |
| FR-43 | 保留中の変更の一覧と、ファイルごとのdiff（行単位、追加/削除/変更）を表示できる | MUST | 2 |
| FR-44 | 変更を個別に破棄できる | MUST | 2 |
| FR-45 | 保留中の変更を選択し、コミットメッセージを付けて1コミットとしてGitHubにpushできる | MUST | 2 |

| FR-47 | 新規ファイルの作成、ファイルの削除・リネームができる | SHOULD | 2 |

| NFR-12 | 50MBのPDFを開ける（初回表示 3秒以内、ページ単位の遅延レンダリング） | 手動計測 |

## 5. 対象外（明示的にやらないこと）

- 端末内でのGit実装（clone, merge, rebase）。Phase 5以降で再検討。
- 端末内でのPython/R実行。
- GitHub以外のGitホスティング（GitLab, Bitbucket）。
- Web版・デスクトップ版（FlutterのターゲットとしてはビルドできてもUI/テストの対象にしない）。
- リアルタイム共同編集。
- 独自の課金基盤（MVPはBYOKで課金なし。ストア課金はPhase 4以降で検討）。

## 6. 主要ユースケース（受け入れシナリオ）

各シナリオは統合テストまたは手動テストの台本として使う。

**UC-1 論文を読む**: ログイン → リポジトリ `research-project` を選択 → `papers/Safron2021/paper.pdf` をタップ → PDFが表示され、ページ送り・検索ができる → AIパネルで「この論文を500字で要約して」と入力 → PDF本文を文脈に回答がストリーミング表示される。

**UC-2 ノートを書く**: `notes/Safron2021.md` を開く → 編集モードに切替 → 数行追記 → 自動保存で「保留中の変更 1件」と表示 → 変更一覧でdiffを確認 → コミットメッセージを入力してpush → GitHub上に新しいコミットができている。

**UC-3 Notebookのエラーを直してもらう**: `notebooks/analysis.ipynb` を開く → エラー出力のあるセルを選択 → AIに「このエラーを修正して」 → AIが `read_file` で関連する `analysis/model.R` を読み、`propose_change` で該当セルの修正を提案 → 提案がdiff付きで表示される → 承認 → Notebookに反映され保留中の変更になる → commit。

**UC-4 分析を実行して確認する（Phase 3）**: Jupyter Server設定済み → Notebookで「すべて実行」 → 出力が更新される → AIに「結果を見て、階層ベイズに変更する案を示して」 → AIが `run_code` で試行し、提案 → 承認 → commit。

**UC-5 リポジトリ横断で探す**: AIに「precisionとpersonalityを扱う資料を探して」 → AIが `search_repo` と `read_file` を使い、該当ファイルの一覧と要約を返す → 回答中のファイル名をタップするとそのファイルが開く。
